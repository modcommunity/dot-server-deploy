# The client shell in a browser

`client/shell.tscn` is the client for every game: a menu, a connection, and whatever game the server sends. [web/README.md](../web/README.md) is how to export and publish it; [releases.md](releases.md) is when a new one is needed.

## What the web player signs in against

`client/auth.json`, shipped inside the export, read by `_sign_in()`, gitignored because it is a deployment's answer. `demo.sh` writes it before the export. It also lists `first_party_audiences`, the INTROSPECT servers (`server:<id>`, the target of the server's site credential) the shell mints a single-use join token for; any other INTROSPECT server is refused with "only gives to its own servers". `tools/shell-auth-json.sh` writes it, from `WEB_SHELL_FIRST_PARTY_AUDIENCES` in CI and `FIRST_PARTY_AUDIENCES` in `demo.sh`.

- **A browser has no environment and no argv**, so `DOT_AUTH_BACKBONE_URL` cannot reach a web client. Without the file it gets `DotAuthConfig`'s exported default.
- **A shipped file, not the page's query string**, for the same reason as `client/content.json`: this URL decides where a single-use sign-in code is redeemed, and a link that could aim it elsewhere would be a credential-forwarding link.
- **It is the SITE origin, not the game origin.** They are deliberately different registrable domains: the game origin is a sandbox that keeps the site's cookies and storage away from the engine. Pointing the backbone at it would send the site's handoff codes to the domain the separation protects them from.
- **The shell calls `try_web_handoff()`, never `DotAuthClient.sign_in()`.** `sign_in()` falls through to a device-code login, which this shell has nowhere to display; it cost two backbone requests on every bare page load.

## Which site the server browsers list

`TmcSiteDefault` (`client/tmc_site_default.gd`) publishes `client/auth.json`'s `backbone_url` as `DOT_BROWSER_BACKBONE_URL` when the shell starts, unless argv, the environment or `?backbone=` already names a site. That is the default for a hand-started shell and for the web, where a game's own fallback of "the page's origin" is wrong: the published game origin is a static bucket that answers `/api/...` with 403 (checked 2026-10-19 against `dotgames.org`), while the site answers the anonymous listing with CORS `*`. tmc-app still passes `--browser-backbone-url` itself. A change reaches players only with a new shell build upload. Test: `examples/solo_check`.

## Solo play

The shell runs one game in the tab with no server: `--solo <owner>/<repo>` (and `--solo-version`) on the command line, or `?solo=` (and `&solo_version=`) on `embed.html`, which forwards it as `--solo`. It is what the site's direct Play button ("Play solo") boots: website-city's `game.boot` puts `boot.solo = {contentId, version}` in the descriptor when there is no server and the app's content is a game pack, and `web/tmc-loader.js` turns that into the query string. The code is `client/tmc_solo.gd` (the request, `latest.json`, the `game.yml` reader, `client/solo.json`) and `client/tmc_solo_session.gd`; `_start_solo` in `shell.gd` drives them.

- **It is a join with the server taken out.** The pack is fetched, verified and mounted by the same `DotCloudClient.ensure` a join uses, so it must verify against the key built into this export; a page can start a different published game and nothing else. With no version, the newest is read from `<base>/<id>/latest.json`, the pointer a publish writes. The bases are the join's: `content.json`'s `content_urls`, else the page's own `/content`. `--content-url <base>` adds one on a desktop launch (never read from the page).
- **The game's own offline mode does the rest.** The shell reads `client_scene` from the pack's `game.yml`, fetches its `dependencies` and `server_dependencies`, instantiates the scene and registers **no** client link: every game decides it is offline by finding none, so a stand-in under `dot_client_link` would make a solo game wait for a server. Bots, the M map menu (solo it changes the map at once), the console and every other offline ability are the game's.
- **Map packs come from `client/solo.json`.** A server names its games' map packs in its own `cfg/content.yml`; a tab has no server, so the shell keeps a copy of the stock lists in `cfg.example/content.yml`, fetches them before the game starts, and publishes their roots in `DotRegistry` under `dot_solo` (`TmcSoloSession.map_dirs(subdir)`). A game reads them by that name, duck-typed, in its offline catalogue (`<Game>Game.solo_map_dirs`), because a delivered game may not name a shell class. `examples/solo_check` fails when `solo.json` and `cfg.example/content.yml` drift. g2gfast is the exception on purpose: one ~50 MB pack per map, fetched by the game when it changes to it. **The fetch is named and the player can decline it.** Measured 2026-10-21 from the site (latest versions, sum of the manifest's file sizes): playground 0.30 MB, wipeout 0.43 MB, deathrun 2.11 MB, prop-hunt 6.26 MB, hide-n-seek 1.59 MB, zombie-zone 2.81 MB, murder-mystery 1.76 MB. The status line reads "Fetching maps: <name> (<size>)" (or "already downloaded") and the download detail under it carries the bytes. A checkbox beside Play solo, "Download this game's maps", is kept per game in `user://tmc_solo.cfg` (`TmcSolo.skip_maps`); on is the default and unchanged, off skips the pack and the game starts with its built-in map(s) only. Test: `examples/solo_check`.
- **Leave goes back to the shell's menu.** Every `DotMenu` built under the game gets the session as its `leave_link` ("Back to menu"), and a client root's `leave_requested` signal is answered the same way. The menu then offers "Play <game> solo" to go again. A game that leaves its own way and hides Leave offline in a browser (g2gfast's `menu_leave_label`) has no in-game way back yet; the site's player close button still works.
- **Subscribed packs (the Workshop) load after the game's own packs and before its scene exists.** The order in `_load_solo`: the shell sets the content index and the content client to the `solo` session, mounts the game pack and its `client/solo.json` map packs, then, only if the game's own `provides.json` has `accepts`, runs `await workshop.sync(game_id)` behind the loading screen (its `progress` signal drives the bar), and only then instantiates `client_scene`, so a catalogue that `follow_content`s the index finds every subscribed map already there. A game without `accepts` is never asked. An online join does the opposite: `_connect_to` sets the session to `online` before anything is fetched and never calls `sync`, and when `requires_restart_before_online()` is true (a subscribed pack that runs code is resident and cannot be unloaded) it writes the join into the addon plan's `resume` and restarts first, as an addon update does. The in-game menu gets a Subscriptions page (`client/tmc_workshop_panel.gd`): per subscription, switches for this game, every game (the site only, on a game-bound web sign-in) and this device, with the state and the reason a pack was skipped. Changes apply at the next launch. **Native builds have no sign-in at all** (`DotAuthWebHandoff.supported()` is web only), so a desktop player is always a guest and the page says "Sign in to use your subscriptions": nightly item `app-native-auth`, noted under `workshop-shell-1`. Test: `examples/workshop_solo`; pictures: `./tools/workshop_shots.sh`.
- **Testing it.** Natively: `godot --headless --path . res://client/boot.tscn -- --solo gamemann/game-arena --content-url https://dotgames.org/content`. In a browser: serve `web/build` with a `/content` that answers on the same origin and open `embed.html?solo=gamemann/game-arena` (`tools/browser_check.mjs` shows the shape).

## The game is not shown until it is ready

A game's first frames are rarely worth seeing: the level arrives after signon, the local body spawns in the air and falls, and under the Compatibility renderer (every browser) each material's shader compiles the first time something draws it, blocking the one thread for hundreds of milliseconds to seconds. `client/tmc_game_cover.gd` (`TmcGameCover`, made by `shell.gd` beside the loading screen) keeps the screen (reason `warm`, no fade-in) over every game until it is ready, then draws its materials once under it. It treats three kinds of game, best first; `mode_of(game)` says which it chose.

1. **A game with a dot-core `DotLoadGate`** ([dot-core docs/loading.md](../../dot-core/docs/loading.md)). The shell puts `dot_load_gate_host` metadata on its game root, so a gate entering the tree under it calls `adopt_load_gate(gate)` on the cover and shows no cover of its own. From then on the gate decides: its `closed` puts the screen up, `progress_changed` is the screen's line and bar, `ready_to_show` (every hold released, every requirement met, a camera in the game, a few physics frames) starts the warm-up here over the tree plus the gate's `warm_items()`, and `host_finished()` tells the gate the screen is down so it unfreezes what it froze and opens. A hold during the warm-up keeps the screen up for the next `ready_to_show`. The gate's own timeout (20 s) and its wait for a host (10 s) mean neither side can leave a player behind a picture. The gate is reached by signal and method name only, so a gate from a newer dot-core overlay works with this shell, and a gate made before the shell claimed the root is found by its `dot_load_gate` metadata on the game root.
2. **The older duck-typed root contract**, which a pack built against any shell can offer: `signal ready_to_show` with `func is_ready_to_show() -> bool` (covered until the signal, at most `WARM_WAIT_SEC`, 20 s, then a warning and shown), and `func warm_up_items() -> Array`, materials and meshes the game will draw later that are not in the tree yet. Each later `ready_to_show` (a map change) warms again without the screen. A gate under a shell from before the gate still works this way: it adds the signal to its root and emits it when it opens.
3. **Anything else.** Covered until the viewport's current camera is inside the game and `FALLBACK_SETTLE_FRAMES` (10) physics frames have run with it, at most `FALLBACK_MAX_SEC` (5 s), then warmed and shown. A game that integrates nothing still never shows its first empty frames; it can show a level that arrives later than its camera, which is what the gate is for.

The warm-up is a dot-core `DotRenderWarmup` hung under the current 3D camera with `PROCESS_MODE_ALWAYS` (the camera is usually under a body the gate froze), which draws every item once, millimetre-sized just past the near plane (culling is by bounds, so the draw and the compile happen; nobody sees it), for two frames. Variants that depend on what lights a surface (a muzzle flash's light) or on skinning are not all reached; the log line `drew the game's materials once under the loading screen` says how many items and how long. The loading screen's own 90 s staleness guard is behind all three.

## Refusals the shell says in words

- `CODE_VERSION` in a disconnect is a kinds or message-types mismatch between two builds that share a signon revision; the shell shows the server's sentence ("This server needs a newer game client.") rather than the build-mismatch message.
- A pack the client is too old to run (`DotCloudClient.failed` with `CODE_VERSION`, from dot-cloud API level 3 before any pack download) is told plainly by `_report_client_behind`, which posts `tmc.build.mismatch` with `reason: "client_behind"`; the loader offers "Reload for the new client" when `boot.builds[0]` is not the running build. Checked in headless Chromium by `tools/loader_check.mjs` (loader half only; the joined path needs the release that bumps `addons.lock`).
- `_cloud.host_role` is `"client"` in the shell and `"server"` in `TmcHost` and `install-games`, so a pack whose `requires.json` asks for more than a build has says which side is behind.

## Clear downloaded content

A mounted pack cannot be unmounted, so a client holding something wrong (a cached object that fails its check, a failed mount, an old copy) is fixed by deleting the downloads and starting again. The menu has a "Clear downloaded content…" button under the status line, and in a game a `FAILED` phase from the shell's content client opens `show_content_failed` with the reason, Dismiss and the same button (mouse freed while it is up).

- It asks first with the size (`downloaded_bytes()`), then `request_clear()` writes `user://dot_cloud_clear_pending` and restarts. **It deletes nothing in the running process**: mounted packs are merged into `res://`, and on Windows an open `.pck` cannot be deleted.
- `clear_pending()` runs first thing in `_ready`, before anything mounts: dot-cloud's `DotCloudStore.clear_all()` and the other cache directories.
- Restart by capability (`DotPlatform.can_self_restart`). A browser reloads through `DotWeb.get_global("location").reload()` a second after asking IndexedDB to flush; **call `reload()` as a method, not `.call("reload")`**, which asks JavaScript for a method named `call`. A desktop build uses `OS.set_restart_on_exit(true, OS.get_cmdline_args())`; `--headless` is not passed on, so testing the relaunch needs a display.

## Layout traps the shell has hit

- **`set_anchors_preset` does not set offsets.** A `Control` built in code keeps the zero size it was created with until something resizes it, so a whole interface can be invisible while correctly configured.
- **A shell feature is a `client/` change**, and `host/` is not in the client build: anything both sides need (cue ids, URL safety) is written twice and a suite checks the copies agree.

## The shell's project.godot

The shell's `project.godot` must keep `audio/driver/enable_input=true`: it is read when the driver starts, so no delivered game can open a microphone without it. The loader's iframe carries `allow="... microphone"`, and a parent page must delegate `microphone` to the game's origin in its own `Permissions-Policy`. [dot-voice design](../../dot-voice/docs/design.md#the-device-layer-and-the-browser)

The shell's `project.godot` carries no comments: the editor drops them, and default-valued keys, the first time it saves the file, so a checkout would show it modified. Its reasons live here: the main scene is `client/boot.tscn` because this project, double-clicked, is the client shell (an operator runs `./server`, which names the host scene), and boot names no addon class because a script compiled before the overlay is mounted keeps its old code for the life of the process ([addon packs](addon-packs.md)); the renderer is `gl_compatibility` because the browser is the whole point of the shell; the two macOS settings are in [native client](native-client.md#two-engine-facts-set-in-projectgodot).

## TLS

A page on HTTPS cannot open `ws://`. Certificates and the reverse proxy are deployment and live in `deploy/`: `issue-letsencrypt.sh` (HTTP-01 out of a webroot, out of nginx, or standalone; DNS-01 through a certbot plugin, the only method that issues a wildcard) and `install-server-tls.sh`. `setup.sh --full` asks whether to do both, and **binds the game to 127.0.0.1 when the answer is yes**: left on 0.0.0.0 the game port stays open beside the TLS one and a client that finds it connects in plaintext. nginx does not carry UDP, so the ENet port (`net_enet_port`, by default the game port number over UDP, shared with A2S and DQP) is reached directly and needs no certificate.

## The browser's audio ceiling

A web build in sample playback runs no bus effects, so dot-audio's Master limiter never runs in a browser, and a pile-up of sounds clipped at the speakers (+3.4 dBFS, 187 clipped samples in 40 s of arena). `export-web` copies dot-audio's `addons/dot_audio/web/dot_audio_ceiling.js` into `web/build/` and makes sure both pages load it before `index.js`: `embed.html` names it in its source, and `install_ceiling` puts the tag into the exported `index.html` (the presets are each box's own copy, so a head include there would reach only new boxes). The script wraps the page's `AudioContext` so the engine's `destination` is a limiter; the measurements are in dot-audio's [docs/loudness.md](../../dot-audio/docs/loudness.md#the-browsers-ceiling). A dot-audio older than the file makes `export-web` warn and build without it.

## Ports and transports

The game listens on `net_port` (6064 in the template) with `net_transport: dual`: browsers on WebSocket/TCP, native clients on ENet/UDP at the same number (`net_enet_port: 0`), with A2S and DQP sharing the UDP port. RCON defaults to the game port plus one. nginx does not carry UDP, so behind TLS the game binds 127.0.0.1 and the ENet port is reached directly. On a panel set every port explicitly. [TLS](#tls), [egg](pterodactyl.md#the-startup-command)

## Which shell a player is running

The shell's menu, the loading screen and the standalone page each carry a small dim line in the bottom-right corner: `shell 20261016-0230 · c09533b`. The commit is stamped by `export-web` and `export-native` into `client/build_stamp.gd` (generated, git-ignored; `-dirty` when the tree had changes). The build id cannot be stamped, because it is chosen at upload after the export: on the web it is read back from the page's path (`/game/<app>/<id>/`, `/godot/<id>/`) and only an exact `YYYYMMDD-HHMM` segment is accepted. Native builds show the commit alone, and a run from source shows nothing. See `client/shell_version.gd`.

The shell fills the resource cache with `DotCloudSliceLoader` (dot-cloud) before it `load()`s a game's client scene in the browser, so compiling a pack's scripts is spread over frames and the loading cover's bar moves instead of freezing for one long frame. Native builds skip it. It needs a dot-cloud that has the loader: `addons.lock` must be bumped to the tag that carries it.
