# Testing

```bash
tools/check.sh                # parse, shell syntax, every suite, then a real boot (./server check)
tools/check.sh --long         # the same, then the long suites (tools/enet_relay_all_games.sh, about 16 minutes)
tools/check_boot_failures.sh  # two boots whose game cannot compile; ./server check must refuse both
tools/package_check.sh        # the same in the shape an operator unpacks
node tools/browser_check.mjs  # the export in a real Chromium against a real server
node tools/browser_update_check.mjs --build <old-lock export>  # the addon update restart, signed in
```

## What each layer proves

- **`examples/selftest.tscn`**: the YAML reader, config translation, permission translation, content index, the game vote's HUD cues, its round-end forwarding from a game whose match it cannot find, the per-game owner settings, the sink layer, the guard, the replay ring and the friends client, against fixtures in `examples/fixtures/`. The fixtures are asserted value by value, so changing one changes a check: they are the exact keys an operator writes checked against the settings they must reach.
- **`./server check`**: a real `DotServer`, a real listener, the default game loaded and its module in it. It also asserts the operator's console (`log`, `sec_status`, `sec_why`, `party_status`, `mm_status`, `replay`), runs `party_status`, fails if the replay ring is not recording, and checks `sv_web_build` and `sv_web_loader` are NOTIFY. An absent command is invisible otherwise: nothing errors until an admin types it during an incident.
- **`./server check` fails on any script error** (exit 7). `TmcScriptWatch` is a `Logger` on the engine's log for the length of a selftest and fails on `Parse Error` / `Could not find base class` / `Failed to load script`, which also catches a broken script that is not the module. dot-server's `load_module` refuses a script that cannot instantiate. A script that fails to parse takes no exit path in Godot, which is how `selftest ok` once printed over a module that never compiled. It cannot catch a parse failure in `host/tmc_host.gd` itself (the scene then never quits), which is why `check_boot_failures.sh` caps each case with `timeout`.
- **`tools/package_check.sh`** exports the tracked files only, runs `setup.sh --vendor`, moves the result away from the siblings, and checks nothing points out of the tree, `addons/` holds real directories, and it boots. It reaches the branch of `check.sh` a developer checkout cannot: no sibling to compare against, so the staleness check reports `--` and must still pass. It does not build the container (needs a Docker daemon).
- **`tools/browser_check.mjs` is the only one that can see the browser**: WebSocket, console and a screenshot. Several of this project's bugs were reachable no other way. A local page cannot fetch game content from the CDN (CORS); see the family notes on local browser testing. `tools/browser_update_check.mjs` serves `/content` through its own proxy, so it reaches a join; it covers the addon update restart and is described in [addon-packs.md](addon-packs.md#the-end-to-end-proof).

## Server-side suites

- `examples/multigame.tscn`: boots buses and switches games; the game vote's rules (`begin_on_apply`, one game = no vote) and its notices at the server.
- `examples/live_switch.tscn`: `changelevel` between games under live players. It names any game it cannot list, offer or vote for.
- `examples/reconnect.tscn`: a client in `PLAYING` is not proof of a join. `DotClientLink` enters `PLAYING` itself after sending `loaded`; the suite also waits for the server session in `SPAWNED` on both connects.
- `examples/game_vote_all.tscn`: the game vote through EVERY game with a real shell attached, each switched into and out of by a click: rock the vote, the game's own ballot waiting and following, the time limit, one entry per game, never two ballots in a frame, the last game's modules gone. Needs every game published in `dist/` (it names any that is not), g2gfast's maps in `dist/maps/<owner>/` (searched by the host since 2026-10-11). About three and a half minutes.
  - `-- --shot=<dir>` under `xvfb-run -a godot --path . --resolution 1280x720` (no `--headless`: a null renderer saves an empty frame) saves `<game>_game.png` once the game ballot is drawn and `<game>_own.png` once the game's own ballot is voting, for every game, and the run is checked as usual. `-- --order=arena,smash,wipeout` plays only those (arena stays first: the fixture boots into it).
  - g2gfast's own-ballot frame shows the shell's loading screen: in one process `DotRegistry` is shared and last-wins, so the server's g2gfast prefetches its map set through the shell's `dot_cloud_client`. A harness artefact, not a client bug.
  - **A scratch copy of the project needs a user folder of its own**: `config/use_custom_user_dir=true` and `config/custom_user_dir_name` in its `project.godot`. With the same `config/name` it shares `user://` with this checkout, the suite removes `user://tmc_game_vote_all` at start and end, and a scratch run beside a real one wrecks the other's packs ("Can't open pack-referenced file"). It also needs its own `net_port` in `examples/fixtures/game_vote_all/net.yml`: every copy listens on 27183.
- `examples/game_vote_rounds.tscn`: the game vote's `time_up: finish_round` through real round ends. Arena, Smash, Prop Hunt and Buses on rounds shortened by their own cvars (`fixtures/game_vote_rounds/content.yml`; arena's round is its whole match, through `arena_timelimit`, `arena_scorelimit` and `arena_warmup`, read back off the running match), a real shell votes the next game in, the game vote must answer whether a round is live as the match does, the clock runs out while the match is LIVE, and the change must wait for that round's `round_ended` and follow it within three seconds. Buses' one runner is given god so its round runs to the clock. Needs `dist/tmc/arena` (from game-arena b7d00ff or later: before it the match cvars reached nothing), `dist/tmc/smash`, `dist/tmc/prophunt` and its maps, and `dist/tmc/buses`. About four minutes. The hold is armed by `round_in_progress` answering false (every game changes at the expiry); breaking only the `round_ended` forwarding does NOT fail it, because the director also polls `round_in_progress_fn` and lets the change go the frame the match leaves LIVE. `selftest`'s "finish_round in a game whose match the game vote cannot find" is the check on the forwarding: a stand-in game (`fixtures/rounds_without_match.gd`, a round-based director and no `DotMatch`) whose change must wait out the expiry and go on its forwarded `round_ended`. Armed by dropping the `round_ended.connect` in `TmcVote._rescan`, and separately by emptying `_on_game_round_ended`: each fails that one check.
- `examples/return_to_game.tscn`: smash, hungario, playground and zombiezone each returned to in one server process with another game in between, and the game's OWN RPC link probed after each return: one link under `Server` on each end at the same path (not `@Node@<n>`), the client's inputs counted on the server's link and the server's snapshots on the client's, then the same for a fresh shell that joins (inputs measured once the first client has left, so they are the fresh one's). The first load is probed the same way. **"The client is in the game" is not netcode**: `_client_in` is the framework's link, and passed with every game link dead. Armed against dot-server 39cecc5 (retire disabled on both ends): 29 failures, every return and every fresh joiner, the first load still passing. About two minutes.
- **The two vote suites count RPCs addressed to a node the other end lacks** (`examples/rpc_path_watch.gd`, a `Logger` installed with `OS.add_logger` for the run): Godot drops such an RPC with three C++ errors and nothing a suite can see otherwise. Both used to pass with `Failed to get path from RPC: Server/@Node@N` in their stderr, which was every client request lost after a rotation came back to a game (dot-server's [game-switching](../../dot-server/docs/game-switching.md#what-a-game-parents-under-server-goes-with-the-game)). A suite that changes games under a client installs it too.
- **Every suite with a server and a client in one process gives the server its own World3D**: `examples/server_world.gd` (`ServerWorld.add(self, _host)` / `ServerWorld.remove(_host)`) puts the host in a SubViewport with `own_world_3d`. Sharing the root's world put the client's copies of the game's bodies in the server's physics space: Buses' server bus hit its client twin and the bowl and fell for ever in `game_vote_rounds`; the other suites passed only because they assert nothing about physics. `multigame` and `party_live` have no client and do not need it. `DotRegistry` is still one per process (see `game_vote_all` above). `DotRegistry` is still shared between the two.
- `examples/addon_entry.tscn`: a server owner's extra packs. `tools/pack.gd` publishes four fixture packs (`examples/fixtures/addon_pack/`: a server-side entry, a client-side entry, no entry, an entry scene that is not in the pack) into a scratch origin; `cfg/addons.yml` and the installer's pins append them to a game's dependencies (defaults first, `remove:` per game, an unpinned one pinned from `data/content-addons.json`); a real `DotCloudClient` mounts them and `TmcAddonEntry.attach` must instantiate only the entry for its side, through the mount prefix, and log (not crash on) the broken one. The entry scene has no script on purpose (a delivered scene cannot name its own files by `res://` path), so it is found by group. Armed by making `attach` ignore `side` and by making `TmcAddonsConfig.apply` append nothing. `selftest` holds the parse checks for addons.yml.
- `examples/pack_requires.tscn`: `tools/pack.gd --source` (what `./server pack` and `setup.sh` run) publishes mg-look-at-me into a scratch directory, and the signed manifest must list `requires.json` with exactly what dot-core's `dot_requires.gd` derives in the source, nothing written into the game's checkout; game-arena's `requires.floor.json` must lower the levels it names; `content/avatars` (not a project) gets none. A first check says the file went through dot-cloud's public `extra_files`. Armed by making `publisher_for` add nothing (the publish fails on the read-back) and by passing it `""` (the manifest check fails).
- `examples/shell_notice.tscn`: the game vote on a real shell's HUD over a real socket, menu and click included, plus clear-downloaded-content.
- `examples/party_live.tscn`: the party booking seam before and after a real `changelevel`.
- `examples/admin_loading_selftest.tscn`, `examples/admin_live.tscn`: [admin-menu.md](admin-menu.md#testing-it).

## A real client in a delivered game

Each `*_client` suite publishes a game from its sibling repository, boots a real `TmcHost`, joins a real client, and asserts the delivery path from the operator's end. The game's own suites cannot reach any of this: there its files are at `res://` and its `class_name` globals are registered. Each says "skipped" and exits 0 when its sibling is absent.

Each window: the share of the client's inputs the server's game link received and of the server's snapshots the client's link received (at least 90% of what the relay let through), ENet's packet throttle at 32 at both ends (also through the join), and the player moved on the server: the link's input counter, plus the path (teleports excluded) of the entity dot-net's registry says the client's peer owns, where there is one (1 m, or 64 px in 2D). dot-game-template's link keeps no counters, so there dot-net's own stand in: the client manager's snapshots received against those it knows it lost, and the server's input buffer for the peer, ticks played with no command against ticks played (its five copies a packet hide 50% loss; armed at 90%). One process per run; the per-game table and logs in `.godot/test-logs/enet_relay_*.log`. Armed at 50% loss up (the inputs check fails alone) and down (the snapshots check), with no key held (the movement check), and by the control (the throttle checks) |
| `burst_probe` (`tools/burst_all_games.sh`) | the most a browser is sent in one frame, per delivered game. A browser's WebSocket peer copies each arriving message into a 64 KiB inbound buffer and drains it once a frame, dropping what overflows ("Buffer payload full! Dropping data."); a native client reads only when polled and never shows it. A real `DotClientLink` on WebSocket through `examples/slow_tcp_relay.gd` with the rate unlimited, polled once a frame: the relay records the most it carried inside any 16.7 ms and in any one poll (one process, so a frame the client spends building piles up exactly as in a browser). Seven windows, in order: the join (connect to seated plus 6 s, and the client's game scene must exist, or only the shell's signon was measured); 10 s of play with the game's stand-ins; seven more real clients joining, each with the game's own client scene, straight to the server, one after another as soon as the last has its scene (a client scene finds its link through `DotRegistry`'s last-wins `dot_client_link`, so seven made at once leave six scenes on one link; look-at-me's and delivery's account keying is switched to the session for this, because every client in one process is one guest); every player's platform avatar changed at once to one with every slot of the game's schema filled and coloured, with `player_avatar_changed` fired for each (the path a site avatar takes when the profile store answers after the seat; "-" for a game with no avatar schema); the scoreboard held open with eight in; the map vote (`revote`, dot-vote's open-now, which every game has: countdown, ballot to all eight, `endvote`, and whatever the close applies); and a change to up to six other maps, through the server world's map-menu call where it has one (`change_course_now`, `change_map_now`, `change_layout_now`, `change_bowl_now`), otherwise as a player does it on M: `/mapmenu` in chat, the list back in notices, then `/mapmenu <id>` with `sv_map_menu_flag` emptied so the guest may change rather than vote (arena, playground, g2gfast, hungario, delivery, look-at-me); the list is asked for again after every change, as M asks on every press, and any row of the list as it is then that is refused fails the maps check (a list walked once chose arena's team modes after a change to dm_pit, which cannot host them). Each window also records its longest frame: with eight clients in one process a frame runs 150-450 ms, and a long frame lets ticks pile into one poll, so the numbers are pessimistic. Each must stay at or under 48 KiB. Prints a `BURST {json}` line; the script prints the table. Armed with `--limit 8000` (under every game's signon): the join check fails alone |

The five games with team combat (`zombiezone`, `prophunt`, `deathrun`, `smash`, `wipeout`) also set the server's `mp_teammate_passthrough` to 2 and 0 live and assert the delivered client's `game.combat.rules` follows it (the game's client calls `combat.follow_cvars(link)`; the game's own suites only see the cvar flagged replicated).

Rules these suites taught:

- **Turn the stdin console off in a fixture.** dot-server's reader is a thread blocked in a read the engine cannot cancel; a suite that shuts the server down with stdin open leaves it destroyed unjoined (one "Thread object is being destroyed" warning).
- **A delivered client needs every addon its game links, linked and imported here.** A checkout that missed a `setup.sh` run (a new addon in the list) or an `--import` after a new `class_name` fails delivered clients in ways that look like the game's bug.
- **A suite must load the game's server scene.** A SCRIPT ERROR in a server scene no game suite loads is invisible to the game's own suites.
- **Check the exit code even when every check passed**: zombiezone's run aborted at exit (`double free or corruption`) because lambdas registered in a static registry outlive their script at engine teardown. Register static-method callables.
- Teardown prints one engine `ERROR: Condition "ready_state != STATE_OPEN"`, from dot-net sending a snapshot in the tick its peer closed. It is dot-net's.

## Arming

Every check added here is armed: the bug is put back and the check must fail, and fail alone. Several first versions passed with the bug in place (comparing two identical clips, a patched PNG failing its own checksum, a CJK name too short to cross the limit). If arming means removing a registration, remove the one the code actually consults.
- `node tools/loader_check.mjs` (set `CHROMIUM` and `PLAYWRIGHT_CORE` off dev01): the loader's "client behind" panel against a stub game origin, with and without a newer build in `boot.builds`. Armed by dispatching on a different `reason`.
