# Addon releases reach players by a restart

**What this platform wants:** a fix to an addon reaches every player by a server restart; a new shell is needed only for the engine, the boot stage or security. Every addon tag is already a signed pack on the content origin (`gamespice-platform/<name>@<version>`, published by the site's release sync; the old `modcommunity/dot-<name>` id is a mirrored alias that gets every new version too, see [Pack ids after the Gamespice rename](#pack-ids-after-the-gamespice-rename)). This is the client side that takes one. dot-cloud's [docs/addon-packs.md](../../dot-cloud/docs/addon-packs.md) has why each dot-cloud piece is shaped the way it is.

## How it works

1. `TmcHost._advertise_addons` reads `addons.lock` and puts one `{dir, repo, id, version}` per installed addon into dot-server's `addon_set`, which rides the signon challenge with `content_base_urls` (so a desktop client knows where to look).
2. The shell's `_on_server_info` asks `DotCloudAddonSet.plan_for` what is newer than this build's own `res://addons.lock` (every export carries it) and than the overlay it already runs.
3. If anything is: it leaves the server quietly, fetches the packs, builds one overlay, writes a plan naming where it was going and who was signed in, and restarts (`_restart`).
4. The main scene `client/boot.tscn` (dot-cloud's `dot_cloud_boot.gd`, which names no addon class) mounts the overlay before anything is compiled and hands over to `client/shell.tscn`.
5. The shell confirms the start, goes back to the server and joins on the newer addons.

## Download groups: only the weapons the game uses

A pack can split files into download groups (dot-cloud's `groups.json`; fc-weapons has one group per weapon, `weapon-<id>`). Once the game's module is loaded, `TmcHost._advertise_addon_groups` asks it for `addon_groups()` (duck-typed: `{dir: [group, ...]}`) and re-announces the set with a `groups` list on those dirs' entries. game-arena names the groups of every weapon its server can hand out.

The shell builds the overlay with the union of what the wanted entries name (`TmcAddonGroups`, `client/tmc_addon_groups.gd`), because dot-cloud takes one group list for a whole overlay:

- **Everything (`*`) when unsure**: no wanted entry names groups (an older server, a game that names none, a failed module), or one names `*` or something malformed.
- **An entry without the field adds nothing.** A pack without `groups.json` has only ungrouped files, which every selection takes. So a game that narrows one grouped pack has to name every grouped pack its server runs; today only fc-weapons (formerly arena-weapons) has groups.
- **Never narrower than the running overlay**: its groups are unioned in, so moving between servers does not restart twice.
- **A group the mounted overlay lacks is a rebuild**, not a top-up: a deferred group cannot be fetched into a mounted overlay. If a server's game needs groups the running overlay was built without (same versions), the shell rebuilds it with the union and restarts, under the same two-restart bound as an update.
- A dot-cloud without groups (0.1.47 and older) has no `groups` property; the shell then sets nothing and takes everything. Solo play builds with everything.

## Only the current game's addons

`addons_announce` (server.yml, `--addons-announce`, `TMC_ADDONS_ANNOUNCE`; `TmcConfig.check_addons_announce` refuses anything but `all` or `game` at boot):

- **`all`** (default, the old behaviour): `addon_set` lists every installed addon, so a joining browser fetches every installed game's packs (fc-weapons ~30 MB, zed ~19 MB, zee 2.5 MB, natural-disasters 0.3 MB) whatever is being played.
- **`game`**: `addon_set` lists the framework's (`dot-*`) addons and the game addons the current game's pack names in its `requires.json` (`TmcAddonSet.scoped`). A built-in game needs none; a game whose `requires.json` is not known yet is announced everything, because too much costs a download and too little a game that cannot load. An addon a game reaches only behind a presence check is optional, is not in `requires.json` and so is not fetched.
- **A game change (a game vote or `game <id>`)** is announced before its content reaches the clients: `TmcHost._announce_change` runs at `game_changing`, or at the next pack's `content_ready` when its `requires.json` was not known yet, and widens `addon_set` to the union of the current and the next game. Every active client that was told less is sent the new set on the `tmc.addons` envelope kind (`TmcAddonGroups.ANNOUNCE_KIND`); the shell takes it as a fresh challenge (`_on_addons_announced`), drops the link, builds the overlay (in place when nothing it replaces is mounted, else the restart above) and rejoins into the new game. A shell that does not know the kind is kicked with a reason saying to rejoin, which then reads the new set from the challenge. After the swap `addon_set` narrows to the new game. A failed load (`game_load_failed`) narrows it back.
- **`sv_pack_pins` keeps every installed addon** in either mode, so the content sweep never removes a pack the next vote may need.
- A second mid-session addition when an overlay is already mounted goes through a restart (a mounted overlay is never replaced in place); mounting a superset in place is a dot-cloud follow-up.

## Rules

- **A desktop relaunch passes both halves of the command line.** `OS.get_cmdline_args()` stops at the bare `--`, and everything this shell reads is after it ([native-client.md](native-client.md#the-launch-arguments-need-the-bare---)).
- **A browser reloads only once IndexedDB holds what the next load reads**: the plan, the overlay and, for a member, the stored session (`_restart(keep)` over dot-cloud's `DotCloudAddonSet.persisted`). One `FS.syncfs` takes seconds and grows with the player's cache, and a reload inside one loses it: the old fixed three-second wait reloaded 2.9 s after the plan was written and came back without it, re-downloaded, restarted again, and joined on the old addons as a guest at the third load. If the files are not there within `PERSIST_TIMEOUT_SEC` (60 s) the shell does not reload, joins on the build's addons and leaves the update for the next start. A `sessionStorage` counter also stops any loop at two. The counter (`tmc.addon_updates`) is kept under the shell build and its addons.lock fingerprint, so a new shell starts it again, and a game's counts are cleared once its addons are running, so updates that worked never count against the next one.
- **A signed-in browser player's stored session is restored after an update restart**, and only for the member the update recorded, because the page's sign-in code is single-use: the site's loader posts the same, now spent, code to the reloaded frame. That depends on the plan (which records the member) and the token store surviving the reload, which is why both are in what the restart waits for.
- **The server box shows where the start is going before sign-in is awaited**, from the page's `?server=` or the plan, so it no longer shows the placeholder for the length of a refused redeem and a restore.
- **No downgrades**: an addon whose version is not newer than the build's is never taken. A server whose lock is older than a player's build leaves them on the newer one, which envelope negotiation handles.
- **An addon pack carries only its own `addons/<dir>/`.** Anything outside it (the weapons pack's art in `res://assets/`) still needs a shell.
- **An addon whose pack is not on the origin is the same as one with no release**: clients keep the build's copy. A game addon (not dot-*) has no build copy, because the shell carries only dot-* addons, so its pack has to be on the origin.
- **A solo game is never started without the addons it needs.** Its scripts do not parse without them: PLAYLOT on shell 20261113-0522 started without zee_weapons and showed a black page, because the tab had already used its two restarts on two updates that had worked. When the overlay cannot be had (two restarts for this set in this shell build, a failed start of it in this shell build, or a build that failed), `_solo_overlay` blocks the start, says why, and the solo button becomes Retry, which forgets that set's count and a failed mark and builds the overlay again. A join still goes on to the server on the build's addons, because a server game can run without them.
- **A failed mark belongs to the shell that made it.** `DotCloudAddonSet.failed_before` matches only the addons.lock fingerprint, so a redeploy that kept the lock kept the mark. The shell stamps the plan it builds with its build id (`shell`), and a mark from another build, or an unstamped one, gets one more try. Tests: `examples/solo_check`; in a browser, `tools/browser_solo_overlay_check.mjs` (fresh, counter2 and failed tabs).
- **A subscribed addon pack joins a solo overlay only in a game that asks for it** (dot-cloud 28). A game whose `provides.json` has `addon` in `accepts.kinds` (PLAYLOT) gets the Workshop's `summary.addons` before its overlay is decided (`_solo_workshop_plan`): approved packs only, already checked by dot-cloud never to replace an addon the build or the running overlay has (a clash is a CONFLICT and an error line, never a silent overlay). `_solo_overlay` adds them to the same overlay as the game's own needs, so one restart covers both, trusts each by its exact id (the site approved it for this player, not its owner), and marks it `source: "subscription"` in the plan. Any other game keeps the refusal (FORBIDDEN) and starts normally. **An online join drops such an overlay**: `_connect_to` restarts whenever the plan holds a subscription, writing a plan in state `dropped` (which the boot does not mount) with the join in `resume`, so the next start is on the build alone plus whatever the server announces. A subscribed addon that is also one the game requires (PLAYLOT requires Natural Disasters) is taken once, at the subscription's version. Test: `examples/workshop_solo` (sections "a game that accepts addon packs" and "does not accept").
- **A solo overlay that only adds addons is mounted without a restart.** A fresh PLAYLOT visit (2026-11-14) fetched the shell, built zee_weapons and arena_weapons (fc-weapons v1.4.46) into an overlay, then said "Restarting to finish the update…" and loaded the shell again: a restart a player with no old version should never see. A restart is needed only because a script already compiled is never read again; an overlay whose addons are all absent from the build, with no overlay mounted yet, replaces nothing, and `load_resource_pack` refreshes the global class list. So `_solo_overlay` mounts such an overlay in place (`_mount_in_place`, which calls `DotCloudAddonSet.mount_now`, dot-cloud API 29: the boot script's steps in one copy), clears the plan's `resume` and starts the game. That covers every first visit and a returning player's first start on a new shell build (whose old plan is for another build and is not mounted). The engine refusing the pack falls back to the restart; a stale probe blocks as a failed boot does. An overlay that replaces a running addon still restarts. Tests: `examples/solo_check` ("mounted without a restart": a class from the mounted pack compiles), and `tools/browser_solo_overlay_check.mjs --state fresh`, which fails on a second load.
- **A join's overlay that only adds addons is mounted without a restart too.** A Fast 4G join to the FC dev server (2026-11-17) built fc-weapons, zed, zee and natural-disasters into an overlay, waited for IndexedDB, reloaded the page, fetched the 26 MB shell again and booted a second engine: about 20 s of a fresh join. `_update_addons` now asks `_join_in_place` first, with the solo path's rule (additive, no workshop subscription): mounted, the restart counts for that server go and the join goes on; stale, the join goes on the build's own addons, as after a failed restart; refused, or an overlay that replaces a running addon (a newer dot-core, a second overlay), restarts as before. Tests: `examples/solo_check` ("a solo game's or a server's addons").
- **Mobile cannot restart itself**: the overlay is written and applies at the next launch.
- **A client exported before this feature has no boot scene** and takes nothing; the first shell carrying it had to be exported the old way.

**One engine line is expected.** A release build logs `ERROR: Attempt to disconnect a nonexistent connection from 'Server' ... 'tree_exited'` once when it leaves a server at the challenge to update. It is the engine's multiplayer cache on an ENet peer closed straight after the first message; deferring the drop does not change it, a debug build does not print it, and the update and rejoin complete.

## Whose packs may replace the build's addons

`TmcAddonNamespaces` (`client/tmc_addon_namespaces.gd`) is the `namespaces` list `DotCloudAddonSet.plan_for` takes an overlay from: the first-party defaults (`gamespice-platform/` and the old `modcommunity/`, plus the game addons published under their author: `gamemann/fc-weapons` (and its old id `gamemann/arena-weapons`), `zee-dot-weapons`, `zed-dot-weapons`, `natural-disasters`; a shell carries none of these, see [web-client.md](web-client.md#the-shell-carries-the-dot--addons-only)) plus what an operator who exports their own shell writes in `cfg/addons/namespaces.txt` (one `owner/` or `owner/repo` per line; the presets already include `cfg/addons/*`). It decides only whose pack may **replace** the shell's own `addons/<dir>`, which then runs for every game the shell plays, from the boot scene, before sign-in. So it is read from the shell build and **never from a server**: a server that could extend it could replace the player's code.

The server side is `cfg/content/addons.yml`: `namespaces:` (the owners the operator trusts; it must match the shell build's file) and `overlays: [owner/repo@version]`, addon packs announced in `addon_set` beside `addons.lock`'s; one replaces the lock's entry for the dir its pack carries (`TmcAddonNamespaces.dir_for`: `gamemann/zee-dot-weapons` is `zee_weapons`, `gamemann/fc-weapons` is `fc_weapons`, or the deprecated legacy `arena_weapons` at a version up to 1.4.51, which still holds it; that use logs a warning naming the ref), so an untagged dev publish can stand in for a lock bump on a dev server. An overlay whose owner is not under `namespaces:` fails the boot. A player on a stock shell refuses it (`refused` in the debug log) and joins on the build's own copy.

Installing by id: `cfg/server/server.yml` takes a plain list, `addons: [gamemann/dot-trail, gamemann/dot-radio@0.1.4]` (`owner/repo[@version]`; without a version the one in `addons.lock` is used). `./setup.sh` clones and pins each one, and the host announces it in `addon_set` like an overlay, so no `addons.yml` is needed. The owner must be trusted (the defaults, or `namespaces:` in `cfg/content/addons.yml`); an untrusted owner, a malformed id, an id with no version, or one `setup.sh` has not installed fails loudly. `gamemann/dot-trail` and `gamemann/dot-radio` are the author-published trail and radio addons (dir `dot_trail`, `dot_radio`); unlike other `dot-*` addons they have no `gamespice-platform/` alias.

It is not what a creator needs. A pack a server owner adds (`cfg/content/addons.yml`, `defaults: add:`) arrives as `content_extra`, is mounted under `res://dot_cloud/<id>/<version>/`, and its `entry` scene is started by `TmcAddonEntry` on the `side` its signed manifest names, with no namespace check: a creator's approved, signed pack already runs in the browser without the shell trusting its owner. Proven on dev with `sp-creator/probe` (`an extra pack started ... side=client`).

If a creator ever needs to replace a shared addon itself, the options are:

- **(a) The site's signed index names the owner of each addon dir.** The site already approves claims per owner; it would sign a `{dir: owner}` list (as it signs packs), and the shell would take an overlay for `addons/<dir>` only from that dir's approved owner. No owner could replace another's addon, and approving a claim stays the one gate. This is the right shape if it is ever wanted.
- **(b) Per-player opt-in** to a third-party overlay. It moves the trust decision onto players, who cannot judge shell code.
- **(c) Keep the first-party list** (current). Nothing a creator ships today needs it.

Deriving the list from the pack's own manifest is not an option: the pack would vouch for itself, so any approved creator could replace any addon by naming its dir.

### Pack ids after the Gamespice rename

The Gamespice packs moved from `modcommunity/dot-<name>` to `gamespice-platform/<name>`. The site keeps the old id as a mirrored `RetiredPackId`, so both ids get every version. `TmcAddonNamespaces.pack_for(dir)` returns the new id as `id` and the old one as `old_id`/`old_repo`; `dir_for_id` maps either back to the dir. Until the steps below are done, the server still **announces the old id** (`announced_pack_for`, used by `TmcHost.addon_set_from`):

- every shell exported so far accepts only `modcommunity/` overlays, and
- `DotCloudAddonSet` matches a pack to the shell's built version by the pack's file name (`dot-<name>`, the `addons.lock` key) and refuses an id whose file name is not the repo. Announcing `gamespice-platform/core` would make every shell refetch every addon or refuse it.

The solo path in `client/shell.gd` resolves the new id first and falls back to the old one. `sv_pack_pins` pins both ids. Switching the announcement to the new ids needs a dot-cloud lookup by lock alias, a newly exported shell, and the site's prod migration (`npm run db:pack-rename:gamespice`).

## The end-to-end proof

dot-cloud's own suite proves the overlay with a run key and separate processes. **The end-to-end proof, an old exported shell meeting a newer server and relaunching onto site-signed addon packs, was done from here:**

- **Desktop**: an exported Linux client whose lock said dot-ui v0.1.4 and dot-audio v0.1.2, against a local `./server` on a newer lock, fetched `modcommunity/dot-ui@0.1.5` and `dot-audio@0.1.3` from the production origin, relaunched, mounted the overlay (2 addons, 29 uids), passed the "the overlay copy is what runs" probe, rejoined by itself and spawned in the FC match.
- **Browser**: the same build in headless Chromium against a local mirror of the two packs: page 1 updated and reloaded, page 2 mounted, confirmed and rejoined, in exactly two loads. A local page cannot fetch game content from the CDN (CORS), so the browser run stops at content sync; that is the known local limit.

Running it found: the launcher in use was the old generated `./server` (regenerate after editing `tools/server.in`); a desktop relaunch lost `--connect`; the browser reload loop above; a signed-in player returning as a guest. All fixed.

**The browser check, `tools/browser_update_check.mjs`.** Export the Web preset from a doctored, older `addons.lock` into a scratch directory (put the lock back), copy `web/embed.html` and dot-audio's `dot_audio_ceiling.js` beside it, start a local `./server run --content-url http://127.0.0.1:8099/content`, and run `node tools/browser_update_check.mjs --build <dir> --server ws://127.0.0.1:<port>`. It serves the build under a host page that hands the frame a single-use sign-in code on every `tmc.auth.ready` (as the site's loader does), a mock redeem endpoint that accepts it once, and `/content` proxied to the CDN. It asserts exactly two loads, the overlay mounted at boot on load 2 with the versions load 1 built, no addon pack downloaded on load 2, the same member signed in on both loads with one accepted redeem, and a join. Armed: a shell from the previous `client/shell.gd` and dot-cloud fails 6 of 8 (three loads, a guest on load 2) on every run; the fix passes 8 of 8.

**The stock-sound overlay, `tools/audio_overlay_proof.sh`.** A project whose dot-audio is the one before the stock sounds (`392f118~1`, no `DotAudioSinkGodot.stream_at`) builds an overlay from the site's published `modcommunity/dot-audio` pack with dot-cloud's `DotCloudAddonSet`, restarts through the boot scene, and plays a stock footstep and bed through `stream_at`. A control run without the overlay must fail the same check. The objects live under the pack's versioned directory, so that directory is a second HTTP base; the content origin rate-limits a dozen parallel downloads of this pack's ~1900 small files, so the proof uses three.

**The same in a browser, `tools/audio_overlay_web_proof.sh`.** Exports a minimal web build (the same old dot-audio, dot-core and dot-cloud, the export templates `./server export-web` uses) with `dot_web.js` and `dot_audio_ceiling.js` in the page head, serves it and `/content` (cached on demand from the real content origin, nothing deployed or pinned) from 127.0.0.1, and drives headless Chromium with playwright-core. The page builds the overlay in IndexedDB, reloads onto it, and plays a stock footstep and bed. The check asserts the build, the mount, `stream_at` and both streams, an AudioContext `running` behind the ceiling's limiter, and a nonzero peak on an analyser tapped on the limiter's output. Run it as `heavy -- tools/audio_overlay_web_proof.sh`. It is not the full shell (no sign-in or game join), only the overlay and ceiling path the shell shares.
